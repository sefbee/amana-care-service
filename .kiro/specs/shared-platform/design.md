## Design

- Preserve Laravel 12 and `app/Admin`, `app/FrontEnd/Cms`, shared `app/Http`, middleware, Blade components and routes convention. Permission checks belong in policies/services in addition to route middleware.
- Model explicit role codes and permission/action scopes. PSU must be a distinct privileged principal/flag/role with break-glass audit hooks; never grant SA via `is_superuser` semantics. Define approved sensitive-action audit event schema before adding modules.
- Permission resolution validates the selected role against the user's active `role_user` assignment and active role row. Cache grants by a monotonically versioned epoch + user id + role id; permission model changes, role-grant updates and assignment model changes advance the epoch so a previous role's cached grants cannot authorize the newly selected role.
- Add reusable policies/query scopes for assigned ownership, minor protection, conflict-of-interest and safeguarding isolation. Validate scopes in controllers, APIs, DataTables, exports, notifications and jobs. SA is explicitly denied sensitive care-recipient access even if a sensitive-data permission is accidentally granted; PSU retains unrestricted access with audit.
- RL-05 uses `record_conflict_blocks` with an explicit staff-user FK and either a Household or Caregiver FK. OM manages the block register; PSU can perform the same actions with break-glass audit. A row lock on the subject user serializes duplicate block creation. Encrypted rationale and revocation reason are retained; history cannot be edited or deleted. `CrmRecordAccess` supplies not-exists scopes and direct-record assertions. Covered paths include CRM duplicate warnings, caregiver/matching/proposal/placement, billing, readiness alerts, and restricted incident related-identity display. Restricted safeguarding cases remain SL/PSU-visible while a blocked caregiver's linked identity and hold controls are withheld from that subject. Export/report/job/API coverage remains open and must use the same scopes before RL-05 can be closed.
- **User-directed deviation (2026-10-27):** TOTP enrollment/recovery and mandatory-role middleware have been removed at the user's explicit request, despite the final SRS requirement. Keep account/session security and login rate limits; record the SRS discrepancy until the SRS/security policy is formally revised.
- General notifications use `operational_notifications` as an encrypted, immutable, idempotent outbox and the user inbox for in-app delivery. Staff recipients may receive in-app/email/SMS; Lead recipients may receive email/SMS only, with current aggregate and exact-channel consent checked immediately before each provider attempt. Email/SMS retries use 1/5/30/120-minute backoff and move to `DeadLetter` after the fifth failed attempt. The every-minute dispatcher uses reservation locks, recovers stale sends, prioritizes urgent rows and writes body-free activity records. External messages are deferred if quiet-hour boundaries are unset or invalid. Generic high priority does not bypass quiet hours; the separate restricted safeguarding dispatcher retains the SRS-authorized bypass. The Platform Superuser has an audited, metadata-only queue monitor that excludes message payloads and recipient details; automatic threshold alerts and production monitoring remain open.
- Scheduled jobs use idempotency keys/unique constraints and distributed locks appropriate to the configured cache/DB driver.
- Executive/Auditor reporting is read-only and aggregate-only: monthly counts for leads, households, placements, issued invoices and reconciled payments, plus aggregate BDT amounts. XLSX output contains no row identities and uses the shared `ExportWatermark` to add exporter ID/time/IP/report ID to workbook metadata and a hidden audit sheet. The SRS's request for a hidden worksheet in CSV is technically undefined; CSV export remains disabled until a format-specific watermark policy is approved.
- **Open operational decision:** the final SRS requires quiet-hour behavior but does not define ordinary start/end times. Do not invent them. Configure `NOTIFICATIONS_QUIET_HOURS_START`, `NOTIFICATIONS_QUIET_HOURS_END`, and timezone after product/operations approval; until then, external notification attempts remain queued. Provider credentials and production delivery evidence are also deployment requirements.
- Consent history is append-only. The active state is the highest-ID record for each channel; an aggregate Lead grant exists if at least one channel's current state is Granted. Outbound Email/SMS log entries lock the Lead and re-evaluate both aggregate and exact-channel consent immediately before recording. Queued provider delivery repeats these checks at send time; approved business trigger wiring, provider configuration and quiet-hour policy remain open.
- Infrastructure controls require deployment evidence; application configuration alone cannot prove TLS, database-volume encryption, backup restore or penetration-test completion.
